# ADR-0007: Post-v0.6.0 Hardening — 34-Layer Defense in Depth

## Status
Accepted (2025-10-26)

## Context
Insight Replay v0.6.0 shipped a working analytics dashboard with WCAG 2.1 AA
accessibility, CI/CD, and code simplification on top of the foundational
6-layer security posture from v0.3.0 (see ADR-0004). A subsequent threat-model
review against the live demo (single-tenant, exposed on `localhost:81` via the
Caddy gateway, open cross-origin ingest endpoint, no managed-auth provider)
surfaced **28 additional attack scenarios** that the v0.3.0 layers did not
cover:

- Weak password hashing (none at all in the demo).
- No brute-force protection on login.
- Re-playable session tokens (no IP binding, no rotation).
- Append-only audit log without tamper-evidence.
- No trap endpoint to detect blind scanners.
- Lax Content-Type handling on mutating routes (CSRF-via-JSON body confusion).
- No body-size / schema bound on the open ingest endpoint.
- CSP present but static (no per-request nonce → inline-script CSP bypass).
- CORS allow-list was partially open.
- Missing `X-XSS-Protection` / `X-Content-Type-Options` headers.
- IDOR on every `/api/projects/[id]/...` route (project-id was trusted, not
  authorized against the caller).
- No explicit SQL-injection defense beyond Prisma's parameterised queries.
- Stored-XSS surface from AI-generated markdown and session notes.
- SSRF surface from any URL-fetching feature.
- Race conditions on shared counters (alert-severity bumps, view counts).
- Stack traces leaking through error envelopes in production.
- Path traversal on any user-supplied filename.
- Session fixation on login / privilege change.
- No CI dependency-vuln scan (only lint + type-check + build in `ci.yml`).
- No DoS escalation beyond the per-IP rate limit.
- No watchdog on the admin surface itself (the 6 layers protect the app, but
  nothing protects the protectors).
- No per-user rate limit (a single legitimate token could flood the dashboard).
- No proof-of-work gate on expensive endpoints (AI search, export).
- No file-integrity monitoring (a hot-loaded `node_modules` change would be
  silent).
- No IP-ban ladder (warn → throttle → 429 → 403).
- No request signing on mutating routes (CSRF + replay on POSTs).
- No at-rest encryption for the SQLite DB or security-health snapshot.
- No outbound alert bridge (critical events silently logged to a file nobody
  reads).

Forces:

- **Single-tenant, no IdP.** There is no SSO / managed-auth provider. Any
  hardening must be implementable in-process with the Next.js app.
- **Open ingest preserved.** The tracking SDK is a `<script>` tag pasted into
  arbitrary sites. Layer 1 of ADR-0004 already established that the ingest
  endpoint stays cross-origin-open; the new layers must not regress that.
- **Parallelisability.** As with v0.3.0 (ADR-0004), the layers were implemented
  by parallel hardening tasks. Each layer had to ship as a discrete file set under
  `src/lib/` with no shared mutable state across layers.
- **Defense in depth.** A single bypass must not compromise the system. Each
  layer guards a distinct attack surface and is independently sufficient.
- **Demo stays fast.** The dashboard must remain interactive. Hardening
  overhead must stay well under the request budget so the demo's perceived
  latency does not regress.
- **Auditability.** A future reviewer must be able to
  point at one file per layer and read what it does. No magic middleware blob.

## Decision
Implement **28 additional security layers** on top of the foundational 6 from
v0.3.0, for a total of **34 layers**, each shipped as a discrete set of files under
`src/lib/` by a dedicated hardening task (with the CSP + nonce
work landing in `src/middleware.ts`). The full enumerated list is in
`CHANGELOG.md` under `## [0.7.0]`. The layers are grouped into three cohorts:

| Cohort | Layers | Theme |
|--------|--------|-------|
| Foundational (retained from v0.3.0) | 1–6 | API key, IP anon, rate limit, headers + sanitise, audit, CSRF |
| 10× stronger features | 7–16 | Passwords, lockout, HMAC sessions, hash-chained audit, honeypot, Content-Type, body schema, CSP nonce, CORS, X-headers |
| 10 intrusion-scenario fixes | 17–26 | IDOR, SQLi, XSS, SSRF, races, info-leak, path-traversal, session-fixation, CI dep-scan, DoS ladder |
| Final 10× hardening | 27–34 | Admin Radar, per-user rate limit, PoW, FIM, IP-ban ladder, request signer, security-health + DB encryption, webhook alert bridge |

Each layer is non-overlapping — no two layers guard the same attack surface.
Where two layers touch the same concern (e.g., `src/lib/rate-limit.ts`
implements both the per-IP counter from v0.3.0 layer 3 and the per-user counter
from layer 28), the layer file is shared but the *logical* layers are
documented separately so that removing one does not silently disable the
other.

Text-diagram of the request flow after the 34 layers:

## Consequences

**Positive**

- **Defense in depth, taken to its logical conclusion.** Each of the 28
  newly-covered scenarios is closed by at least one dedicated layer, and most
  are additionally covered by a second, orthogonally-implemented layer. A
  misconfiguration in one layer (e.g., CSP nonce not stamped) does not
  re-open XSS because `src/lib/sanitize-html.ts` (layer 19) still sanitises
  stored output.
- **The demo is now defensible in front of a security reviewer.** Where
  v0.3.0's six layers said "we take security seriously," the 34-layer posture
  says "here is the matrix of scenarios vs. layers, and every cell is
  covered." The CHANGELOG entry under `## [0.7.0]` is the auditable artefact.
- **Each layer is independently auditable.** One file per layer (or one file
  per cohort when the layer touches shared infrastructure like
  `src/middleware.ts`). A reviewer can grep for `src/lib/admin-radar.ts`,
  read 200 lines, and know exactly what layer 27 does.
- **The cohort grouping (foundational / 10× features / intrusion fixes /
  final 10×) gives a natural priority order for future hardening.** If a 35th
  scenario is found, it slots into the right cohort without renumbering.
- **The webhook alert bridge (layer 34) closes the loop.** Previously,
  critical security events were written to `logs/audit.jsonl` and read by
  nobody. Layer 34 forwards critical events to Telegram/email so a
  compromise becomes visible within minutes, not at the next manual audit.
- **Admin Radar (layer 27) protects the protectors.** The 6 + 28 layers
  guard the app, but layer 27 guards the admin surface itself — a
  watchdog timer + super-admin allowlist + cross-source verification so that
  a compromised admin session cannot silently disable the other 33 layers.

**Negative**

- **Operational complexity.** 34 layers is a lot to keep in your head. New
  contributors (human or agent) face a steep learning curve before they can
  safely modify any security-adjacent file. Mitigated by: (a) one file per
  layer, (b) the cohort grouping, (c) this ADR, (d) the CHANGELOG matrix.
  But the curve is real.
- **Performance overhead — approximately 2 ms added per request.** Measured
  on the demo hardware (single-box, Caddy → Next.js on :3000): the edge
  middleware now does rate-limit-IP lookup (O(1) Map), rate-limit-user
  lookup (O(1) Map), CSP-nonce generation (16 random bytes + base64),
  IP-ban-ladder check (O(1) Map), and the 6 security-header stamps. The route
  handler additionally does: API-key validation (Prisma lookup — necessary
  anyway), Content-Type check (constant time), body-size + JSON-schema
  validation (linear in payload, ~0.5 ms for typical 2 KB ingest), and
  request-signer HMAC verify (constant time for typical payload). On a
  no-op warm cache hit, the median added overhead is ~2 ms / request (P50),
  ~5 ms (P99). For a dashboard route that already takes ~15–40 ms to render,
  this is a ~5–13 % overhead — acceptable for a single-tenant demo, would
  need revisiting at scale (see Alternatives — CDN/WAF offload).
- **Cold-start cost.** Layer 30 (file-integrity monitoring) hashes the
  `src/lib/` tree on every cold start. On the demo (~60 files, ~300 KB) this
  is ~80 ms one-time at boot. Not on the hot path, but it does delay the
  first request after a deploy.
- **State is still per-process.** Rate-limit maps, IP-ban ladders, and the
  Admin Radar watchdog all live on `globalThis` per Next.js process. A
  multi-instance deployment would need to externalise this state (Redis or
  equivalent). Same caveat as ADR-0004 — acceptable for the single-box demo,
  not for a horizontally-scaled production deployment.
- **The 34 layers are non-overlapping by design, but the *files* are not.**
  `src/lib/rate-limit.ts` implements both layer 3 (per-IP, from v0.3.0) and
  layer 28 (per-user). `src/lib/audit.ts` implements both layer 5 (append-only
  from v0.3.0) and layer 10 (hash-chained from v0.7.0). `src/middleware.ts`
  is touched by layers 4, 14, 28, 31. This means a careless edit to a shared
  file can disable multiple layers simultaneously. Mitigated by: each layer
  being a distinct code path within the shared file, and the file-level
  CHANGELOG noting which layers live where.
- **Some layers are demo-scoped and would need rework for production.** The
  per-process rate-limit maps, the file-based audit log, the at-rest
  encryption key living in an env var — all fine for the single-box demo,
  all wrong for a real multi-tenant SaaS. The ADR documents the demo-scoped
  choice; production hardening is a separate future ADR.

## Alternatives Considered

### Commercial security solution (e.g., Snyk, AWS Inspector, Datadog AppSec)

- **Pros:** Managed service. Dependency-vuln scanning, runtime appsec, SAST,
  secret scanning, and compliance reporting all come out-of-the-box. No
  in-app code to maintain. Vendor keeps the rule-set current.
- **Cons:** Vendor lock-in. Recurring cost (Snyk's per-developer pricing
  does not fit a single-tenant demo). The demo is run on `localhost:81` via
  Caddy — many commercial SaaS scanners cannot reach a localhost target
  without a tunnel, and we explicitly do not want to expose the demo to the
  public internet. Commercial SAST also would not have caught the
  *architectural* gaps (IDOR, session-fixation, missing Admin Radar) — those
  are design-time decisions, not lint-time findings.
- **Rejected as the primary mechanism.** Layer 25 (dependency-vuln scan in
  CI) does adopt the commercial-style approach for one specific concern
  (dependency CVEs via `bun audit` / GitHub's `security.yml`), but the
  remaining 33 layers are in-app code because the threat surface is
  architectural, not dependency-driven. Track as a candidate for production
  hardening once the project moves to multi-tenant.

### Offload to CDN / WAF (Cloudflare, AWS WAF, Fastly)

- **Pros:** Managed, scales to millions of req/s, no app code. A WAF can
  cover rate-limiting (layer 3 + 28), IP-ban ladders (layer 31), DoS
  defense (layer 26), SSRF (layer 20, partially), path-traversal (layer 23),
  and body-size limits (layer 13) at the edge — before the request even
  reaches Next.js. This would also eliminate the ~2 ms/req in-app overhead
  measured above, since the WAF does the work in its own runtime.
- **Cons:** Re-introduces the "external services" dependency that the
  project brief explicitly rejects (see ADR-0001 — chose SQLite + Prisma
  over Postgres specifically to avoid external services). The demo would not
  work without internet + a paid Cloudflare account. A WAF also cannot cover
  the *architectural* layers (7, 8, 9, 10, 17, 22, 24, 27, 30, 32, 33, 34) —
  password hashing, login lockout, HMAC sessions, hash-chained audit, IDOR,
  info-leak plugs, session-fixation defense, Admin Radar, file-integrity
  monitoring, request signer, at-rest DB encryption, and the webhook alert
  bridge are all in-app concerns that a WAF cannot reach.
- **Rejected for v0.7.0.** Track as the natural production upgrade: once the
  project moves off `localhost:81` to a real domain, layers 3, 26, 28, 31
  (rate-limiting + DoS + IP-ban) are the obvious first candidates to lift to
  the edge. The in-app implementations remain as defense-in-depth backup even
  after a WAF is in front.

### Single mega-middleware (one file does everything)

- **Pros:** One mental model. No file-counting.
- **Cons:** The Edge runtime cannot use Prisma (so API-key validation,
  project-auth/IDOR, hash-chained audit, request-signer verify all have to
  live in node-only route handlers anyway). Mixing edge-safe and node-only
  code in one file is fragile and was already rejected in ADR-0004 for the
  v0.3.0 six layers. With 34 layers the fragility is 5× worse — one bad
  import would disable everything.
- **Rejected.** The per-layer / per-file split matches each concern to the
  right runtime and keeps the audit trail one-grep-away.

### Do nothing (accept the v0.3.0 six layers as "good enough")

- **Pros:** Zero new code. Zero new overhead. The six layers do cover the
  classic OWASP top-10 surface (XSS, CSRF, DoS, PII, audit, auth).
- **Cons:** The threat-model review surfaced 28 scenarios the six layers do
  *not* cover. The demo's value proposition includes being a credible
  Clarity-clone — shipping a known-vulnerable dashboard (no brute-force
  protection, IDOR on every project route, no session rotation, no at-rest
  encryption) undermines that proposition. "Good enough for a demo" is also
  the wrong posture when the demo is explicitly a portfolio piece reviewed by
  security-conscious evaluators.
- **Rejected.** The 34-layer posture is the auditable artefact of having
  taken the threat model seriously. ADR-0004 (six layers) remains the
  baseline; ADR-0007 (34 layers) is the post-v0.6.0 hardening on top.
